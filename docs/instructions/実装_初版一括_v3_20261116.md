# 指示：schedule-roadmap-builder 初版の一括実装（v3：自走優先）

## 0. この指示の位置付け（必ず最初に読む）

- 正本は `docs/specification.md`（v0.3）である。以前の指示書（v1、v2）は使わない。
- これまでの経緯と、作成済みのコードは `docs/progress.md` を参照する。
  - 作成済みのファイルは、捨てずにそのまま使う。
  - 作成済みのコードは未検証なので、ビルドとテストで確認しながら進める。
- **本指示に限り、copilot-instructions.md にある「適用役は設計の判断をしない」「不明点は停止」のルールを緩める。** 仕様の範囲内であれば、実装の詳細を自分で判断して進めてよい。
- 利用者は、途中で承認したり回答したりしない。**環境の問題やライセンスの確認を理由に止まらないこと。** まず自分で解決を試み、それでも解決できないものは記録して先へ進める。
- 判断した内容と、自分で回復した手順は、すべて `docs/progress.md` の「実装時の判断メモ」に記録する。

## 1. 停止条件（次の3つだけ）

1. .NET 9系のSDKが無い。
2. 3.1の回復手順をすべて実施しても、NuGetの復元が成功しない。
3. §2.1にも推移的依存にも当たらないパッケージが、新たに必要になった。

上記以外は止まらない。ビルドエラーやテストの失敗は、直るまで自分で修正する。

**同じ問題を5回直しても解消できない場合**
- 該当するテストに `Skip`（理由付き）を付けるか、該当する機能を最小限の実装にとどめる。
- その内容を記録して、先へ進める。

**停止する場合の報告**
- 停止するときは、次の5点を日本語で報告する。
  - 停止した理由
  - 判断に必要な事実（コマンドの出力など）
  - 取りうる選択肢と、それぞれの影響
  - 推奨する案
  - 再開する手順

## 2. 禁止事項

- git の操作。
- ファイルの削除（後述の obj/bin の例外を除く）。
  - 不要になったファイルは、削除せずに `_tmp_` という接頭辞を付けた名前に変えて残す。
  - 共有のNuGetキャッシュ（`%USERPROFILE%\.nuget\packages`）は、削除もクリアもしない。
- §2.1 に無いパッケージを直接参照として追加すること。
- 仕様書 §12 にある対象外の機能の実装。
- 実際の案件名・人名の使用。
- MCPの使用。

## 3. 手順

### 3.1 NuGet復元の回復手順（前回のエラー「既に存在するファイルを作成することはできません」への対応）

1. 詳細なログを出して再実行する：`dotnet restore ScheduleRoadmapBuilder.sln --disable-parallel -v detailed > _tmp_restore1.log`
2. 1が失敗した場合は、このプロジェクト専用のパッケージ保存先を使う。
   - ソリューション直下に `Directory.Build.props` を作成し、`<RestorePackagesPath>$(MSBuildThisFileDirectory).nuget-packages</RestorePackagesPath>` を設定する。
   - 共有キャッシュには手を加えない。
   - 設定したら、`--disable-parallel` を付けて再実行する。
3. 2も失敗した場合は、プロジェクトを1つずつ復元する（Core → App → Tests の順）。
   - ログから衝突しているファイルが分かった場合は、そのプロジェクトの `obj` に限り削除してよい。
   - 名前を変えて退避する方法でもよい。
4. 3までで成功しない場合のみ、停止条件2として停止する。

成功したら、次の内容を判断メモに記録する。
- 原因の推定
- 効いた手順
- `Directory.Build.props` を作成した場合はその内容

### 3.2 ライセンスの確認（止めずに記録する）

- `dotnet list package --include-transitive` で、全パッケージを確定する。
- 各パッケージのライセンスを、仕様書 §2.2 の方法で確認する。
- xunit.abstractions 2.0.3 は、nuspecにlicense要素が無い。次の順で確認する。
  1. licenseUrl
  2. パッケージに同梱されたファイル
  3. どちらでも確定できない場合は「要確認」と記録して先へ進める。
- 記録する内容
  - `THIRD_PARTY_NOTICES.md`：パッケージ名、バージョン、ライセンス、確認方法、確認日、配布物に含むかどうか
  - `licenses/<パッケージ名>-<バージョン>/`：入手できたライセンス原文

### 3.3 実装の順序（各段階で `dotnet build` と `dotnet test` を通してから次へ進む）

1. 作成済みのコア部分（モデル、日程計算、CW、表示モード）をビルドとテストで確認し、修正する。
2. JSONの保存と読み込み（`.bak` の作成も含む）、祝日の取り込み、テスト。
3. メイン画面（表とカレンダー）、行の操作、設定画面。
4. PNG出力とテスト。
5. PPT出力とテスト（OpenXmlValidatorを使う）。
6. `samples/sample.srb.json` を作成し、このサンプルからPNGとPPTを生成するテストを用意する。
