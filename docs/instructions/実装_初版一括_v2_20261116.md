# 指示：schedule-roadmap-builder 初版の一括実装（v2：推移的依存の扱いを反映）

## 0. この指示の位置付け（必ず最初に読む）

- 正本は `docs/specification.md` である。本指示と正本が矛盾する場合は、正本を優先する。
- **本指示に限り、copilot-instructions.md にある「適用役は設計の判断をしない」というルールを緩める。** 仕様の範囲内であれば、クラス構成・画面レイアウトの細部・描画方式などの実装の詳細を自分で判断して進めてよい。
- 利用者は、途中で承認したり回答したりしない前提で作業を任せている。下記の「停止条件」に当たらない限り、止まらずに最後までやり切ること。
- 判断に迷った点は、最も単純で仕様に反しない案を選んで進める。選んだ内容は `docs/progress.md` の「実装時の判断メモ」に記録する。

## 1. 停止条件（これに当たる場合のみ停止して報告する）

1. `docs/specification.md` が存在しない。
2. .NET 9系のSDKが無い（`dotnet --list-sdks` で確認する）。
3. NuGetの復元が失敗する（ネットワークやプロキシの問題など）。
4. 仕様書 §2.1 のパッケージのライセンスが、仕様書の想定と違う。§2.1 にも §2.2 にも当たらないパッケージが必要になった。§2.2 の推移的依存のライセンスが、§2.2 で認めた種類以外だった。
5. 同じビルドエラーまたは同じテストの失敗を、3回直しても解消できない。
6. 仕様書の内容どうしが矛盾していて、どちらを選んでも仕様に反してしまう。

停止するときは、次の5点を日本語で報告する。

- 停止した理由
- 判断に必要な事実（コマンドの出力など）
- 取りうる選択肢と、それぞれの影響
- 推奨する案
- 再開する手順

## 2. 禁止事項

- git の操作（このプロジェクトはgit管理をしていない）。
- ファイルの削除。自分が作った一時ファイルも、削除せずに `_tmp_` という接頭辞を付けて残す。
- 仕様書 §2.1 に無いパッケージを直接参照として追加すること。§2.2 の条件を満たす推移的依存は許可する。
- 仕様書 §12 にある対象外の機能の実装。
- 実際の案件名・人名の使用。
- MCPの使用。

## 3. 手順

### 3.1 下準備

- `docs/specification.md` を読む。
- `dotnet --list-sdks` を実行する。

### 3.2 `.github/copilot-instructions.md` の「TODO(要確認)」を、次の内容で置き換える（他の行は変更しない）

| TODO | 置き換える内容 |
|---|---|
| UI技術など | WinForms / net9.0-windows / xUnit / PPTはDocumentFormat.OpenXml |
| 資料どうしの優先順位 | `docs/specification.md` ＞ `docs/instructions/` の指示.md ＞ その他 |
| サンプルデータの方針 | 架空のデータのみ使う（仕様書 §14） |

`csharp.instructions.md` の規約の詳細のTODOは、次の内容で置き換える。

- nullableを有効にする。
- 命名は.NETの標準規約に従う。
- 非同期処理は使わない（必要になった場合のみ使う）。
- 警告は0件にする。

### 3.3 ソリューションの構成（推奨。理由があれば変えてよい）

```
ScheduleRoadmapBuilder.sln
src/ScheduleRoadmapBuilder.Core/     … モデル、日程計算、CW、祝日の取り込み、JSON、PPT・PNG出力の生成ロジック（UIに依存しない）
src/ScheduleRoadmapBuilder.App/      … WinFormsの画面
tests/ScheduleRoadmapBuilder.Tests/  … xUnitのテスト
samples/sample.srb.json
```

- PNGの生成ロジックは、System.Drawingを使うためCoreに置く。Coreのターゲットは `net9.0-windows` でよい。

### 3.4 実装の順序（各段階で `dotnet build` と `dotnet test` を通してから次へ進む）

1. モデル、稼働日カレンダー、日程計算（仕様書 §6）、CW、テスト。
2. JSONの保存と読み込み（`.bak` の作成も含む）、祝日の取り込み、テスト。
3. メイン画面（表とカレンダー）、行の操作、設定画面。
4. PNG出力とテスト。
5. PPT出力とテスト（OpenXmlValidatorを使う）。
6. `samples/sample.srb.json`。このサンプルからPNGとPPTを生成するテストも用意する。

### 3.5 第三者コンポーネントの記録

- `dotnet list package --include-transitive` を実行し、推移的依存も含めた全パッケージを対象とする。
- 導入した各パッケージについて、次の内容を `THIRD_PARTY_NOTICES.md` に記載する。
  - パッケージ名、バージョン、ライセンス、確認した日
  - 確認した場所（URL）
  - 配布物に含むかどうか
- ライセンスの全文を `licenses/<パッケージ名>-<バージョン>/` に保存する。

### 3.6 README.md の作成（日本語）

次の内容を記載する。

- 概要。
- 使い方の流れ：新規作成 → 設定 → 項目の入力 → PNG出力・PPT出力。
- exeの作成コマンド。次のコマンドを基本とする。
  `dotnet publish src/ScheduleRoadmapBuilder.App -c Release -r win-x64 --self-contained false -p:PublishSingleFile=true`
- exeが出力される場所。

### 3.7 最終確認

1. `dotnet build -warnaserror` が成功すること。
2. `dotnet test` が全件成功すること。
3. 3.6のpublishコマンドが成功すること。publishの出力は `publish/` に置く。

### 3.8 docs/progress.md への追記

次の内容を追記する。

- 実施内容
- テストの件数（passed / failed / skipped）
- 作成したexeのパス
- 実装時の判断メモ
- 未完了の作業

## 4. 完了報告（日本語）

次の内容を報告する。

- 作成した主なファイルの一覧
- テストの件数
- exeのパス
- 実装時の判断メモ（要点のみ）
- **人が確認する項目のチェックリスト**：仕様書 §13.2 をもとに、手順として書く。確認に使うファイルは `samples/sample.srb.json` とする。
